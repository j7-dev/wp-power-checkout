# Clarify Session 2026-06-18 11:00

## Idea

把開源 SDK `paid-tw/einvoice`（台灣電子發票統一 TypeScript SDK）的設計優點，評估並導入本專案 `power-checkout`（WooCommerce 發票外掛，PHP 8.1 / DDD）的 Invoice 領域。需求訪談 + 規格化產出，串接後續 planner。

### 背景：兩專案已完成深度架構比較（既有結論，不重做研究）

根本分叉：einvoice 輸入是 pure DTO（orderId+buyer+items+amount）、框架無關、可 throw；power-checkout 輸入是 `\WC_Order`、綁 WC hook 生命週期、provider 層 never-throw（怕斷結帳）。導入優點時必須尊重 PC 的 never-throw 契約與 WC 整合架構。

einvoice 經證實的設計優點（已讀原始碼佐證）：
- 正規化錯誤模型：單一 `InvoiceError extends Error`，帶 `code`（9 種正規化 enum：AUTH/VALIDATION/NOT_FOUND/CONFLICT/NUMBER_EXHAUSTED/NETWORK/PROVIDER/UNSUPPORTED/UNKNOWN）+ `rawCode`/`rawMessage`/`raw`（保留 provider 原始碼供 debug）+ `isInvoiceError` type guard。各 adapter 把自家錯誤碼 map 成正規化 code（Amego 數字區間、ECPay 中文訊息 regex）。
- 共用執行期驗證：所有 adapter `issue()` 第一行跑共用 Zod schema——UBN checksum、手機條碼格式、carrier/donation 互斥、`salesAmount+taxAmount===totalAmount` 金額守恆，跨 provider 一致。
- 有狀態 MockProvider：in-memory 狀態機（issue→void→CONFLICT、雙索引支援 orderId 查詢、真跑 schema 驗證），是 fake 不是 stub。
- capability 模型：`ReadonlySet<Capability>` 11 種細粒度（含 FOREIGN_CURRENCY/SCHEDULED_ISSUE/MIXED_TAX）+ `supports()`/`assertSupports()`。

### PC 現況（已盤點，作為 baseline）

- 介面 `Domains/Invoice/Shared/Interfaces/IInvoiceService.php`：`issue()`/`cancel()`/`get_invoice_number()`/`get_settings()`，全回 `array`，失敗一律回 `[]`（資訊塌縮——金鑰錯/網路斷/驗證失敗無法區分）。
- capability：marker interface `ISupportsAllowance`/`ISupportsQuery` + `instanceof`。
- 4 provider：Amego(MD5)/Ecpay(AES-128-CBC)/Ezpay(AES-256-CBC+CheckCode SHA256)/Paynow(Bearer JWT)。
- 加密重複：ECPay AES-128-CBC 邏輯在 Invoice/Ecpay + Payment/Ecpg 兩份檔案，Logistics 複用 Payment/Ecpg（程式碼註解自承的技術債）。ezPay AES-256-CBC 刻意獨立，不在抽取範圍。
- 測試 `tests/Integration/Invoice/`：API_MODE=mock 回 fixture stub（非狀態機）；Amego 測試部分缺。
- 驗證散在各 provider，無統一執行期驗證層（已有 checkout 表單級 `Shared/Helpers/InvoiceParamsValidator.php`，但缺 UBN checksum / 互斥 / 金額守恆）。

## Q&A（4 個用戶獨有決策，已由用戶定案 = max scope）

- Q: 導入範圍（4 項全做 / 只做高 CP 值 / 分階段）？ → A: **全做 4 項**——#1 正規化錯誤物件 + #2 共用驗證層 + #3 狀態機 MockProvider + #4 抽 ECPay AES 到單一 Shared。
- Q: 錯誤契約改造的相容性偏好（保留 `[]` 並加旁路 vs 改 `WP_Error` vs 結果物件）？ → A: **WP_Error**——成功回 `array`、失敗回 `\WP_Error`（攜帶正規化 `code` + `rawCode` + `rawMessage`，塞 `$error_data`）。呼叫端加 `is_wp_error()` 判斷。須更新所有既有呼叫端：`ProviderRegister` auto-issue/auto-cancel hook、`woocommerce_order_refunded` 折讓 hook、REST `/invoices` 端點回應、Vue InvoiceApp/MetaBox 前端對應。
- Q: 是否連帶處理 Payment 領域的同類錯誤模型？ → A: **Invoice + Payment 一起**——錯誤模型設計成跨領域共用，正規化 `code` enum + 基底錯誤類別放 `inc/classes/Shared/`（領域中立）。兩領域都套用。Payment 領域更大（7+ 金流 provider、NotifyURL always-200、退款/3DS/capture/void），錯誤模型須容納金流場景（callback 驗簽失敗、退款不支援、金額守恆等）。
- Q: 驗收與測試期望？ → A: **嚴格**——標準（每 provider 錯誤碼→正規化 code 映射測試 + 驗證層 UBN/互斥/守恆獨立測試 + 既有全套測試不退化）+ 升級 MockProvider 為狀態機補狀態流測試（issue→void→CONFLICT）+ 補齊 Amego 缺漏測試。掛 error/edge group。

## 技術約束（專案規範）

`declare(strict_types=1)`、`final class`、PHP 8.1+ enum/readonly、PHPStan L9、text domain `power_checkout`、hook 用 static method `[__CLASS__, 'method']`、PSR-4 `J7\PowerCheckout` → `inc/classes/`。錯誤 `code` 用 backed enum；WP_Error 的 `$code` 字串用該 enum value，`$data` 帶 `rawCode`/`rawMessage`/`provider`/`raw`。

## 訪談期間核實的關鍵技術事實（讀原始碼確認）

1. 資訊塌縮實證：`Ezpay/Services/EzpayInvoiceProvider.php` 13 處 `return []`，涵蓋驗證失敗 / response 型別不符 / API 例外 / 發票未開立 / 無折讓資料，全塌縮成同一回傳，呼叫端無法區分。
2. AES 抽取（#4）精確邊界：三個 `AesCrypto.php` 中，`Invoice/Ecpay`（AES-128-CBC base64）與 `Payment/Ecpg`（AES-128-CBC base64）演算法相同 → 可合併；`Ezpay`（AES-256-CBC hex blocksize=32）docblock 明確警告不可合併 → 不在抽取範圍。Logistics 已複用 `Payment/Ecpg`（見 erm.dbml line 337）。抽取目標 = ECPay AES-128-CBC 單一化，三處（Invoice/Ecpay + Payment/Ecpg + Logistics）共用。
3. never-throw 契約實證：`PaynowInvoiceProvider` docblock「catch \Throwable → logger（同步 order note）→ 回 []，絕不破壞 WooCommerce 主流程」。新模型把「回 []」換成「回 WP_Error」但保留 never-throw。
4. Payment 已有 WP_Error 先例：`IPaymentProvider::process_refund()` 回 `bool|\WP_Error`，docblock「不應 throw」。新模型形式化並豐富化（正規化 code 入 `$error_data`）。
5. REST 現況：`InvoiceApiService` 直接 `WP_REST_Response($result, 200)`，不檢查失敗。改造後須檢查 `is_wp_error($result)` 並映射為錯誤回應（既有 feature 斷言 `回應狀態碼為 500` 將演進為斷言回應體帶正規化 `error_code`）。
6. 既有 Gherkin 慣例：中文關鍵字（`功能/規則/場景/假設/而且/當/那麼`）+ 檔頭 `# language: zh-TW`；Activity 用 `.activity` DSL 格式。新規格沿用此慣例。
