## Idea

PAYUNi UPP = UNiPaypage = 導轉式（整合支付頁，瀏覽器跳轉到 PAYUNi 託管頁），與綠界 AIO / 藍新 MPG 完全同型。技術參考已就緒：payuni-upp-v2 skill（AES-256-GCM 加解密、SHA256 HashInfo、UPP 請求/回傳參數、所有付款方式、交易查詢/請退款/取消授權、Sandbox 測試）。

## 第一性原理推理 trace（Q1=B 的決策依據）

基本事實（不可再分的前提）：
1. power-checkout 有三個整合領域：Payment、Logistics、Invoice。
2. Logistics 領域有顯式豐富 interface `ILogisticsProvider`（10 方法）。
3. Invoice 領域有顯式豐富 interface `IInvoiceService`。
4. Payment 領域目前只有極簡 `IGateway`（單方法 process_payment）+ 完全空的 marker `IGatewaySettings`，且 `AbstractPaymentGateway` 本身未 implements `IGateway`。

推導：
- 從「同一專案的三個 provider 領域應有一致的抽象哲學」這個第一性原則出發，Payment 領域是唯一缺乏豐富顯式 provider interface 的例外。
- 此不一致不是本質需求差異造成的（金流 provider 同樣有 process/refund/query/capture/void/get_settings 等共同行為，完全可抽象），而是歷史演進的偶然。
- 因此引入 PAYUNi 這支新金流時，正本清源地抽出 `IPaymentProvider`，並讓既有 4 支金流對齊，是最符合第一性原理的選擇。

## 登記：回歸風險（Q1=B 的代價，planner 必須納入）

- **影響面**：既有 4 支金流（shopline_payment_redirect、ecpay_aio、ecpay_ecpg、newebpay_mpg）全部要改 implements `IPaymentProvider`。
- **風險**：4 支既有金流的付款/退款/callback 行為可能因介面契約變動而回歸破壞。
- **緩解策略（交 planner 規劃）**：
  1. `IPaymentProvider` 抽象須涵蓋既有 4 支金流「已實作能力」的最大公約數，能力差異（如 SLP 無 capture、ATM 無 API 退款）以「回傳 unsupported / WP_Error」表達，不強迫每支都實作。
  2. 漸進遷移：先定義 interface → AbstractPaymentGateway implements 並提供預設實作 → 既有 gateway 逐支驗證 → 最後 PAYUNi 新增。
  3. 測試保護：既有金流的 Integration test（tests/Integration/）須在 refactor 前後皆綠燈；refactor 視為「行為等價重構」，不得改變對外行為。
