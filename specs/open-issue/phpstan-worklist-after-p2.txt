### 關鍵第一性原理結論（不是漏跑，是型別層本來就不會亮）

把 IInvoiceService / ISupportsAllowance / ISupportsQuery 的 5 個方法回傳型別
從 `array` 改成 `array|\WP_Error` 後，PHPStan L9 **沒有**新增任何 error。原因是
PHPStan 只在「呼叫端把結果當 array 用」的型別邊界（subscript `$r['k']`、foreach、
傳給要求嚴格 array 的參數）才會亮 error；而本專案目前所有呼叫這 5 個介面方法的
地方，都不構成這種邊界：

  1. `InvoiceApiService` 5 個 REST callback（行 74/93/114/130/153）：
     `$result = $service->issue($order);` → `new \WP_REST_Response($result, 200);`
     `\WP_REST_Response::__construct(mixed $data = null, ...)` 收 `mixed`，
     `array|\WP_Error` 餵 `mixed` **不違型**。$result 從未被 subscript / iterate。
  2. `ProviderRegister::maybe_issue_allowance_on_refund`（行 132）：
     `$provider->issue_allowance($order, $refund_amount);` → 回傳值**直接丟棄**
     （無 assign、無 consume）→ 無型別邊界。
  3. auto-issue / auto-cancel（行 188/196）：
     `\add_action("woocommerce_order_status_{$status}", [$provider, 'issue'|'cancel'])`
     → provider 方法是 **WP hook callback 本體**，`do_action` 丟棄回傳值，
     PHPStan 不把 WP hook dispatch 當 typed consumer → 無型別邊界。

  ※ 各 provider 內 `$client->issue(...)` / `$client->cancel(...)` 等是呼叫
    **HTTP ApiClient**（`InvoiceApiClient` / `ApiClient`，簽名 `?IssueResponse` 等
    未變動），不是介面方法，與本次型別變更無關，不在 work list。

  ※ provider 實作方法仍宣告 `: array`，是 `array|\WP_Error` 的合法協變窄化
    （PHP 回傳型別協變），不 fatal、PHPStan 也不報 method.childReturnType。
    → 符合 P2 設計：P4 才把 provider 簽名改成 `array|\WP_Error` 並實際回 WP_Error。

### 結論：本階段 work list = 「語義型」呼叫端缺口（P4/P5 用），非「型別型」缺口

因為 PHPStan 型別層此刻無新 error，P4（provider 改回 WP_Error）+ P5（呼叫端加
is_wp_error）要消化的「work list」不是來自 PHPStan diff，而是來自下方人工盤點的
**呼叫端語義缺口清單**。待 P4 讓 provider 真的 `return WP_Error` 後，這些呼叫端
若仍把結果當成功 array 用、或直接把 WP_Error 塞進 200 回應，才是真正要補的洞
（屆時部分會由 PHPStan 在「P4 之後」亮出，部分純屬契約語義需手動補）。
